### D2 — Google sign-in depends on `URL.searchParams`, unimplemented in RN — **FIXED**
`mobile/src/services/auth.ts:131-132` · HIGH · crash

I traced the constructor path for a custom-scheme URL like `wagerpals://oauth-callback?access_token=...` (no `base` arg passed, so the un-validated branch is taken, `this._url = url` directly) and confirmed `.search`/`.searchParams.get('access_token')` resolve correctly. The crash the finding describes cannot reproduce on the RN version actually shipped, even though the suggested fix (add the polyfill package) was never applied. This is a fix by version, not by intent — flagging for awareness in case RN is ever downgraded.

### D9 — Sessions cannot survive access-token expiry — **FIXED**
`mobile/src/services/api.ts:153-176`, `lib/auth.ts:48-63` · HIGH · correctness
The mobile client now sends both tokens on every request: `Authorization: Bearer <accessToken>` plus `x-stack-refresh-token: <refreshToken>` (`api.ts:160-174`). Server-side, `resolveAuthenticatedStackUser` in `lib/auth.ts:56-60` passes both into Stack Auth: `stackServerApp.getUser({ tokenStore: { accessToken, refreshToken } })`, which Stack Auth uses to transparently mint a new access token when the old one is expired but the refresh token is still valid. This is a legitimate silent-refresh design (server-side token exchange on every call) rather than the client-side refresh-on-401 the audit suggested, but it closes the same gap: an expired access token no longer permanently breaks the session.

### D10 — Auth can commit a user with an empty ID — **FIXED** (mitigated downstream, not at the cited line)

The practical outcome — a confusing signed-in-but-broken state with a blank identity header — can no longer occur; the user is bounced back to the auth screen instead.

### D11 — iMessage-created events bypass the group membership check — **FIXED**
`mobile/src/screens/CreateEventFromInviteScreen.tsx:342-343`, `mobile/src/services/api.ts:465-478` · HIGH · security

Caveat: the server route still only enforces membership conditionally on `creator_user_id` being present rather than unconditionally deriving it from the session — a non-mobile caller that omits the field entirely would still bypass the check — but that is a broader design point outside D11's specific mobile-bypass claim, which is closed.

`app/api/groups/route.ts:15-70`, `app/api/groups/members/route.ts:98-108` · CRITICAL · privacy

Of the three routes cited, only one is actually fixed: `GET /api/comments?eventId=` (`app/api/comments/route.ts:118-134`) now calls `loadAuthedEventContext` (which runs `requireAuth`) and explicitly checks `if (!group.is_public && !isActiveMember) return 403`.
