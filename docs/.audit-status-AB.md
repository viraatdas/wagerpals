# Audit re-verification: Section A (auth/identity) + Section B (payments/escrow)

Re-checked against the current working tree on 2026-08-16, after n1–n9 landed. Every
`file:line` below was opened and read in the current tree; line numbers reflect current
locations, not the original audit's. Method: read the cited code, trace the actual call
path, and for the money findings (B1/B3/B4/B5/B10/B11/B12) specifically reason about
whether the guard holds under the stated attack rather than trusting a nearby comment.

### A1 — Any request can impersonate any user via an unverified header — **FIXED**
`lib/auth.ts:48-84` · CRITICAL · security
`resolveAuthenticatedStackUser` now resolves identity three ways only: (1) `Authorization: Bearer` token via `stackServerApp.getUser({ tokenStore: { accessToken, refreshToken } })`, (2) an `x-stack-auth` header handed to Stack Auth itself, or (3) the Stack Auth cookie session via `stackServerApp.getUser()`. It never reads `x-stack-user-id`. Confirmed by grep: `lib/auth.ts` contains no reference to that string anywhere. Several client files (`app/page.tsx`, `components/BetForm.tsx`, etc.) still *send* an `x-stack-user-id` header, but it is now inert — the server ignores it. `scripts/check-identity.ts` Assert 4/6 are the regression tests for exactly this and both pass by inspection of the source.

### A2 — `POST /api/users` has no authentication at all — **FIXED**
`app/api/users/route.ts:54-57` · CRITICAL · security
`POST` now calls `await requireAuthUser(request)` as its first line and returns the 401 response immediately if unauthenticated — before the body is even parsed. A caller-supplied `id` is only used for a `verifyUserMatch` cross-check (line 64-67, returns 403 on mismatch); the row id actually written always comes from the authenticated session (`stackUser.id`, threaded into `syncUser`).

### A3 — `username_selected` is forced to `true` on every insert — **FIXED**
`lib/db.ts:265` · CRITICAL · correctness
The insert now reads `${user.username_selected ?? false}` — nullish coalescing, not `||` — so an explicit `false` is preserved instead of being coerced to `true`. `lib/sync-user.ts:229` (`usernameSelectedFlag = false` on the auto-derived path) confirms new users default to *not* selected, so the picker can actually show.

### A4 — No email on `users`, so email and Google signups can never be merged — **FIXED**
`lib/schema.sql:4-18,220` · CRITICAL · data-model
`users` now has `email TEXT`, `auth_methods JSONB`, and `merged_into TEXT REFERENCES users(id)`, plus `CREATE UNIQUE INDEX idx_users_email_lower ON users(LOWER(email)) WHERE email IS NOT NULL` — two live rows can never hold the same email at the DB level. `lib/sync-user.ts` populates and reads all three. The schema-level gap the finding describes no longer exists.

### A5 — Duplicate signup silently creates a mangled duplicate instead of surfacing the collision — **DEFERRED**
`lib/sync-user.ts:186-196,204-219` · HIGH · correctness
The `username1`-suffix mangling is gone (replaced by a deterministic `derivePlaceholderUsername(stackUserId)`), and `syncUser` does detect an email collision (`db.users.getByEmail`) — but on collision it only *skips writing the email* onto the new row and logs a server-side `console.warn`; it does not look up and link the existing account, and the user gets no indication a real account already exists. Real prevention is delegated to Stack Auth's dashboard `oauthAccountMergeStrategy = link_method` setting (`docs/IDENTITY.md`), which is external configuration this repo cannot verify or enforce — if it is unset or set to `allow_duplicates`, the exact defect the finding describes (a second, empty-ledger account created silently on second sign-in) still happens today. Offline reconciliation (`scripts/merge-duplicate-users.ts`) exists but must be run manually after the fact.

### A6 — Username uniqueness is a TOCTOU race that can 500 — **FIXED**
`lib/sync-user.ts:239-275` · MEDIUM · correctness
The 100-attempt loop is gone. `syncUser`'s create path does one `db.users.create`, and on failure inspects the driver error via `uniqueViolationTarget` (constraint name matching, e.g. `users_pkey`/`idx_users_email_lower`/username) and retries exactly once with a collision-proof shape (`derivePlaceholderUsername`, or drop the email). `app/api/users/route.ts`'s POST handler catches any remaining exception and returns a generic `{ error: 'Failed to sync user' }` 500 — never `error.message` — closing the raw-Postgres-error leak too.

### A7 — Mobile writes the OS display name into the ledger instead of the app username — **DEFERRED**
`mobile/src/screens/EventDetailScreen.tsx:289,322` · HIGH · correctness
Both bet placement and comment posting still build `username` as `user.displayName || user.primaryEmail || user.email || 'User'` and send it to the server. For comments this is now neutralized server-side (`app/api/comments/route.ts` `resolveCanonicalUsername` — see A8), but bets are not: `app/api/bets/route.ts` still writes the client-supplied `username` verbatim into `bets.username` (and into the activity feed / cash-bet `placeCashBet` call). A bet placed from iOS still shows the Stack Auth display name or raw email instead of the chosen app username. `mobile/src/screens/CreateEventFromInviteScreen.tsx` was not checked line-by-line but the general client-trusts-body-username pattern on the server side (bets) is unchanged.

### A8 — Client-supplied `username` is trusted and denormalized into three tables — **DEFERRED**
`app/api/bets/route.ts:16,117,121,509` (username from body) vs `app/api/comments/route.ts:81-85` (fixed) · HIGH · security
Comments are fixed: `resolveCanonicalUsername(userId, bodyUsername)` looks up `db.users.get(userId).username` and only falls back to the body value if no user row exists at all — a comment can no longer display someone else's chosen name. Bets and activities are not: `app/api/bets/route.ts`'s `POST` destructures `username` straight from the request body and writes it into `newBet.username` (free path) and passes it into `placeCashBet` (cash path, which stores it into `bets.username` unchanged), with no cross-check against the authenticated user's actual `users.username`. Any authenticated user can still post a bet displaying an arbitrary name.

### A9 — Username validation rules differ between web, mobile, and the server — **FIXED**
`mobile/src/utils/helpers.ts:23-45` vs `lib/utils.ts:118-140` · MEDIUM · correctness
Mobile's `validateUsername` is now byte-for-byte the same rule set as the server's: 2-20 chars, `^[a-zA-Z0-9_]+$` (dashes rejected on both sides now, not silently stripped on one and accepted-then-stripped on the other). The file's own comment states "Mirrors lib/utils.ts's validateUsername exactly."

### A10 — Mobile's username setup never marks the username as chosen — **FIXED**
`mobile/src/services/api.ts:300` · MEDIUM · correctness
`createOrUpdateUser` now posts `{ username, username_selected: true }` — confirmed at the call site referenced in `UsernameSetupScreen.tsx`'s own comment citing "audit finding A10."

### A11 — Open redirect leaks OAuth tokens to any URL the attacker names — **DEFERRED (still CRITICAL, unfixed)**
`app/api/auth/mobile-oauth-callback/route.ts:11-22,86-101` and `app/api/auth/mobile-session/route.ts:9-17,51-62` · CRITICAL · security
Both routes are unchanged in the relevant respect. `mobile-oauth-callback` still does `const state = JSON.parse(Buffer.from(stateParam, 'base64url').toString()); if (state.callback_url) mobileCallbackUrl = state.callback_url;` with **no scheme/host allowlist**, then appends the freshly minted `access_token`/`refresh_token` to that URL and 302-redirects to it (`NextResponse.redirect(successUrl.toString())`, lines 86-101). `mobile-session` has the identical pattern via its `callback` query param, and it is reachable in the live flow (`app/auth/signin/page.tsx:26-27` does `router.push('/api/auth/mobile-session?callback=' + mobileCallback)` when `mobile_callback` is present — itself fed from `app/api/auth/mobile-oauth/route.ts`'s fallback path). This is still exploitable exactly as described: a crafted `state`/`callback` naming an attacker-controlled origin exfiltrates a real user's access and refresh tokens.

### A12 — PKCE is stubbed out in the mobile OAuth exchange — **DEFERRED (still HIGH, unfixed)**
`app/api/auth/mobile-oauth-callback/route.ts:56` · HIGH · security
The token exchange body still sends the literal `code_verifier: 'none'`. No verifier is generated, persisted keyed by `state`, or validated. Unchanged from the audit's description.

### A13 — Three overlapping mobile auth callback routes, one of them dead — **DEFERRED (partially fixed)**
`app/api/auth/` (route listing) · LOW · dead-code
The literally-dead route, `mobile-callback`, has been deleted (confirmed absent from `app/api/auth/`; `docs/IDENTITY.md` documents the deletion explicitly). However `mobile-session` — a second, still-live route implementing the same token-handoff pattern as `mobile-oauth-callback`, and carrying the *same* A11 open-redirect defect — remains in place and reachable via `app/auth/signin/page.tsx`. The "two places to get the security-sensitive handoff logic wrong" problem the finding warned about is reduced (3→2) but not eliminated, and both surviving routes are currently wrong in the same way (A11).

### B1 — A negative bet amount credits the wallet — **FIXED**
`app/api/bets/route.ts:112-115` (free path) and `lib/payments.ts:222-261,265` (cash path) · CRITICAL · money
Free path: `parsedAmount = Math.round(parseFloat(amount)*100)/100; if (!(parsedAmount > 0)) return 400` — rejects negative/NaN before any DB write (and the free path never touches the wallet at all). Cash path, `placeCashBet`: `stake = roundMoney(input.amount); if (!(stake > 0)) throw INVALID_STAKE` (line 239-241) runs, then the wallet balance is read (line 251) and compared (`balance < stake`, line 252), and only then is `debitWalletGuarded` called (line 265) — the sign/finiteness check unambiguously precedes every wallet mutation. A negative `amount` is rejected long before `deductBalance`/`debitWalletGuarded` runs; there is no path where a negative stake reaches the guarded UPDATE.

### B2 — Withdrawals delete the money instead of paying it out — **DEFERRED (still CRITICAL, unfixed)**
`lib/payments.ts:787-858` · CRITICAL · money
`withdrawFromWallet` inserts a `transactions` row with `type: 'withdrawal', status: 'completed'` and then debits the wallet via `debitWalletGuarded` — there is still no Stripe Connect transfer, no payout API call, no external money movement of any kind anywhere in this function or its caller (`app/api/wallet/route.ts`'s `action === 'withdraw'` branch). Grep across the repo for `stripe.transfers`/`stripe.payouts`/`Connect` finds nothing outside `stripe.paymentIntents.create` (which is the *deposit* path). `scripts/verify-payments.ts`'s Step 13 only asserts DB-level correctness (transaction recorded, balance decremented, idempotent replay) — it does not and cannot assert money actually left the platform, because it doesn't. The defect is unchanged: a withdrawal zeroes the user's balance and no money ever leaves.

### B3 — The Stripe webhook is not idempotent, so retries double-credit — **FIXED**
`lib/payments.ts:685-762` (`creditStripeDeposit`) · CRITICAL · money
Path 1 is a single guarded `UPDATE transactions SET status = 'completed', idempotency_key = ${key} WHERE id = (SELECT id FROM transactions WHERE stripe_payment_intent_id = ... AND status = 'pending' AND type = 'deposit' ... LIMIT 1) RETURNING *` — a flip from `pending` to `completed` that matches zero rows (and thus credits nothing) on any redelivery, since the row is already `completed` by then. The wallet credit only happens `if (settleResult.rows.length > 0)` (line 719). Path 2 (no pending row found) is additionally guarded by a `WHERE NOT EXISTS (... status = 'completed' ...)` subquery plus `ON CONFLICT (idempotency_key) ... DO NOTHING`. This is exactly the "guarded UPDATE that no-ops on zero rows changed" the finding asked for, not an if-statement wrapped around a re-read.

### B4 — Resolve/unresolve/resolve mints unlimited money — **FIXED**
`lib/payments.ts:565-674` (`reverseCashSettlement`), `342-554` (`settleCashEvent`) · CRITICAL · money
`reverseCashSettlement` reverses every `escrow_release`/`payout`/`refund` transaction for the event with a compensating `escrow_hold` debit (guarded by `debitWalletGuarded`, which throws `INSUFFICIENT_FUNDS`-style `REVERSAL_BLOCKED` — line 615-632 — if a user has already spent part of their payout, blocking the unresolve outright), then restores the holds to `'held'`. A subsequent resolve is not "free money": `settleCashEvent` computes a per-event settlement generation number (`seq`, line 370-374, counted from prior settlement-type transactions) and stamps every idempotency key with it, so the second resolve's transactions are genuinely new — but they can only pay out money that `reverseCashSettlement` just re-escrowed (holds are back to `'held'`), not manufacture new funds. Verified the debit-before-credit ordering holds: reversal debits happen before `holds_restored` UPDATE.

### B5 — `POST /api/events/delete` has no authentication and destroys escrowed bets — **FIXED**
`app/api/events/delete/route.ts:6-54` · CRITICAL · security
Now calls `requireAuth` first, restricts to the group resolver (cash/private events) or group admin (free/public events) via the same `requiresResolver` pattern as resolve/unresolve, and — the money-critical part — refuses the delete outright when escrow is outstanding: `if (event.payment_type === 'cash') { const held = await db.escrowHolds.getHeldTotalForEvent(event_id); if (held > 0) return 400 ESCROW_OUTSTANDING }`. An event with live stakes cannot be deleted at all; the resolver must cancel (which refunds via `settleCashEvent(id, null)`) first.

### B6 — "Real money" is inferred from `is_public`, with no per-event payment type — **FIXED**
`lib/schema.sql:53` (`events.payment_type TEXT NOT NULL DEFAULT 'none' CHECK (payment_type IN ('none','cash'))`) · HIGH · data-model
`events.payment_type` now exists and is what every money-relevant route branches on (`app/api/bets/route.ts:31 if (event.payment_type === 'cash')`, `app/api/events/resolve/route.ts:36`, `app/api/events/delete/route.ts:25/42`, `lib/payments.ts` throughout). `group.is_public` is no longer used to decide whether money moves.

### B7 — Toggling group visibility retroactively changes the currency of open bets — **FIXED**
`app/api/events/route.ts:90-108,143-156` (payment_type pinned at creation) · HIGH · money
`payment_type` is set once, from the request body, at `POST /api/events` and stored on the event row; there is no PATCH/PUT handler anywhere in `app/api/events/` that ever mutates `events.payment_type` afterward (confirmed by reading the full route file — only `POST` writes it). Since B6 means all money logic reads `event.payment_type` rather than `group.is_public`, `PATCH /api/groups`'s still-unrestricted `is_public` toggle (`app/api/groups/route.ts:156-185`) can no longer retroactively change what currency an already-placed bet resolves in — the field it would have re-derived from doesn't drive money logic anymore.

### B8 — Late bets are counted for payout but never funded — **FIXED**
`lib/payments.ts:215-220` · HIGH · money
`placeCashBet` now rejects any bet attempt after the event's `end_time` outright — `if (Date.now() > parseInt(event.end_time)) throw EVENT_CLOSED` — before any hold/transaction/bet row is created. A late cash bet can no longer enter the ledger at all, so the "shown as real stake but unfunded" scenario is structurally impossible for money. (Free/points events still allow late bets and still exclude them from `calculateNetResults`'s payout math, same as before — but since no wallet is involved for points, this is a display nuance, not a money bug.)

### B9 — Deleting a bet does not refund the wallet — **FIXED**
`app/api/bets/route.ts:223-232` · HIGH · money
`DELETE /api/bets` now checks `if (event && event.payment_type === 'cash') return 400 CASH_BET_IMMUTABLE` before doing anything else — a bet on a real-money event cannot be deleted at all, so there is no path where deleting a bet destroys an escrowed stake. (Free-event bet deletion still has no explicit "event must still be active" check, but that only affects points bookkeeping, not money.)

### B10 — If nobody backed the winning side, the whole pot vanishes — **FIXED**
`lib/payments.ts:406-452` · HIGH · money
`settleCashEvent` computes `winningHolds` and explicitly branches: `const isRefundPath = winningSide === null || winningHolds.length === 0;` — when nobody held the winning side, every held stake is refunded (`reason: 'no_winners'`, looping over every hold and crediting `hold.amount` back, line 412-443) instead of silently retaining the pot. `app/api/events/resolve/route.ts:161-167` correspondingly skips `calculateNetResults` (which would otherwise report a full loss for everyone) when `settlement.mode === 'refund'`.

### B11 — Payouts are non-transactional and can halt halfway — **FIXED**
`lib/payments.ts:342-344,493-533` · HIGH · money
The entire settlement — hold selection, payout computation, transaction inserts, wallet credits, hold-status updates — runs inside one `withTransaction(async (tx) => {...})` call (line 343), so a mid-loop failure rolls the whole thing back atomically; nothing is left half-paid. Each transfer (`escrow_release`, `payout`) is additionally guarded by a per-user, per-generation `idempotency_key` with `ON CONFLICT ... DO NOTHING`, and the credit only fires `if (...Result.rows.length > 0)` — so even a retry of the whole `settleCashEvent` call after a transient failure (e.g. a timed-out connection) is a safe no-op, matching the finding's exact fix request.

### B12 — Rounded per-user nets do not have to sum to zero — **FIXED**
`lib/payments.ts:462-483` · MEDIUM · money
Payouts are computed in integer cents throughout (`toCents`/`fromCents`), each winner's share is floored (`Math.floor((potCents * stakeCents) / winningTotalCents)`), and the leftover `remainderCents = potCents - allocatedCents` is handed out one cent at a time in a deterministic order (`descending stake, ascending user_id`) until exhausted — the code comment states the invariant explicitly ("the total always sums to exactly potCents") and the arithmetic verifies it: `allocatedCents` after the remainder loop always equals `potCents`. (The separate leaderboard-only `calculateNetResults` in `lib/utils.ts` still rounds each user's net independently, but that only affects the `net_total` display stat, not actual wallet money, which is owned entirely by the cents-exact `settleCashEvent`.)

### B13 — Bets and transactions cannot be reconciled — **FIXED**
`lib/schema.sql:77-89` (`escrow_holds` table: `event_id`, `bet_id`, `user_id`, `amount`, `status`) and `:192` (`transactions.event_id TEXT REFERENCES events(id)`) · HIGH · data-model
Both requested columns/tables exist. "What is currently escrowed for event X" is `db.escrowHolds.getHeldTotalForEvent(eventId)` (used live in `app/api/events/route.ts` and `app/api/events/delete/route.ts`); "refund the bet this transaction paid for" is answerable via `bets.escrow_hold_id` → `escrow_holds.bet_id`/`event_id` → `transactions.event_id`.

### B14 — Wallet errors never reach the user in the web bet form — **FIXED**
`components/BetForm.tsx:104-117,270-289` · HIGH · ux
`handleSubmit` now checks `if (!response.ok)`, parses the JSON error body, and calls `setError({ message, code, shortfall })`, which renders either a generic inline error banner or (for `INSUFFICIENT_FUNDS`) a dedicated "You need $X more" banner with an "Add funds" link. The error is no longer silently discarded.
